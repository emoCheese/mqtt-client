# 06 · 设计取舍：为什么不用更简单的做法

> 本文回答两个常被问到的问题：
> **① 为什么需要保活、引用计数、两段等待这些"复杂"机制？**
> **② 为什么不把代码写得更简单直接？**
>
> 结论先给：**不是"不以简单可靠为核心"，而是当四个需求同时成立时，"看起来简单"的写法
> 只是把复杂度从库内转移到了每一个业务回调里，转移之后更难验证、更难保证可靠。**

## 6.1 复杂度的来源：四个同时成立的需求

| 需求 | 直接后果 | 若砍掉它，能省掉什么 |
| --- | --- | --- |
| **通用**：任意 `Svc`（含 const 成员函数）+ 任意可调用对象 | 目录层只能 `void* + 函数指针` 类型擦除 ⇒ 库**不拥有**目标对象 ⇒ 必须显式管理生命周期 | 用虚接口 + `shared_ptr` 就能简化生命周期（但引入继承与分配） |
| **零拷贝**：高频消息不复制 payload | `MessageView` 是借用视图 ⇒ 必须显式延长数据寿命 | 每题消息深拷贝一次，生命周期问题消失一半 |
| **允许回调内再注册**：handler 里 `open()`/`close()` 不死锁 | 派发期间**不能持锁**执行用户代码 ⇒ 需要"计数 + 等待"而不是一把锁 | 一把 `shared_mutex` 全程持有，代码最短 |
| **允许异步**：handler 可投递线程池 | 调用帧 ≠ 工作结束 ⇒ 必须引入可随数据流动的引用计数凭据 | 文档禁止异步，删掉 `Lease`/`async_refs` |

四条都要，就只剩"显式生命周期协议"这一条路。

## 6.2 被否决的"简单方案"

| 方案 | 代码量 | 为什么不用 |
| --- | --- | --- |
| **A. 薄封装**：paho + `map<topic, std::function>`，回调里自行处理 | 最少 | ① 不支持同 topic 多播；② 生命周期完全甩给用户，每个业务回调都要重复写"加锁 / 拷贝 / 判活"；③ 通配匹配、重连订阅补齐都要用户自己写 |
| **B. 强制深拷贝**：每条消息造 `Owned` 交给 handler | 少 | **只解决"数据悬垂"，解决不了"目标对象悬垂"**：异步任务里的 `this` 照样 UAF；且每条消息每 handler 一次分配 + 拷贝（高频场景不可接受） |
| **C. 派发全程持锁**（`shared_lock` 覆盖 `h->fn`） | 少 | ① handler 内 `close()` 立即死锁（`shared_mutex` 不可重入，回调内再注册是硬需求）；② 任一慢 handler 阻塞所有注册/摘除 |
| **D. 目录持有 `shared_ptr<Service>`** | 中 | ① 绑定语义变拥有语义：谁创建 service、重复注册同一 service 怎么办、如何表达"外部对象"？② 仍然不解决消息数据寿命；③ 强制所有业务对象走堆分配 |
| **E. 禁止异步**（文档规定 handler 必须同步完成） | 少 | ① 约束被违反时是 **UAF 而不是编译错误**，靠人守不住；② 慢处理会堵死唯一消费线程，把可用性问题变成稳定性问题 |
| **现行方案** | 多 | 把协议**收敛到库内一处**（约 100 行），并且可以被并发用例 + ASan/UBSan/TSan 覆盖 |

一句话对比：

> A/B/C/E 的"简单"是把风险**摊到 N 个业务 handler** 上（无法集中测试、缺陷只在压力下暴露）；
> 现行方案是把风险**收敛到 1 处**，代价是这 1 处必须被证明正确——而"可被证明"正是它值得复杂的原因。

## 6.3 复杂度账单（不粉饰）

| 机制 | 存在理由 | 代价 | 可否移除 |
| --- | --- | --- | --- |
| `Slot::inflight` + 两段等待 | 区分"调用帧"与"派生工作" | 一个额外计数器 + 一条顺序不变式 | 若禁止异步可去掉第二段 |
| `Slot::async_refs` + `Lease` | 让库能观测用户线程池的存续 | 每次 handler 调用一次小分配（几十 ns） | 若禁止异步可整段删除 |
| `KeepAlive` 类型擦除 | 避免 `message.hpp` 依赖 paho 的 async_client；让"按值捕获"自动生效 | 多一层间接 | 可换成直接持有 `const_message_ptr`（污染数据层依赖） |
| `thread_local t_active_slot` | 回调内自析构不能自等 | 隐式线程状态，可读性下降 | 若禁止回调内析构可去掉（但需求明确要求支持） |
| `BatchGuard` 异常兜底 | 分配失败时不能泄漏 `inflight`，否则 teardown 永久挂起 | 多一层 RAII | 若接受"bad_alloc 即崩溃"可去掉 |
| `wild_filters_` 单独索引 | 让无通配的常见路径零额外开销 | 一份冗余索引，需与 `dir_` 同步 | 可改为每次全表扫描（消息量大时不可接受） |
| `session_subs_` + `connected_once_` | 重连既不漏订阅、也不重复触发 retained | 一份会话状态 | 若接受"每次重连全量订阅"可去掉（代价是重复 retained） |

**诚实的评价**：这套协议的**理解成本**是真实存在的。它的价值只有在
"多播 + 高频 + 线程池"三者中出现两个时才兑现（见 §6.4）。

## 6.4 什么时候**不值得**这个复杂度

| 场景 | 建议 |
| --- | --- |
| 单进程小工具：消息量低、handler 都是毫秒级同步处理 | 直接用 paho + 一个 `std::function`；本库是过度设计 |
| 明确禁止异步 handler，且团队规模小 | 保留目录，删掉 `Lease`/`async_refs`（§6.5 档位 1） |
| 不需要同 topic 多播、不需要回调内再注册 | 删除 `Entry.handlers` 向量与引用计数（回到 `mqtt_client0` 形态） |
| 只订阅固定几个具体 topic，不涉及通配 | 可移除 `wild_filters_` 与 `topic_filter.hpp` 的扫描路径 |
| 数据可以随便拷贝，性能不敏感 | 用"档位 2"：`MessageView` 换成 `Owned`，借用视图从 API 中彻底消失 |

反过来，出现以下任意两条，显式生命周期协议就是必需品：

- 同一 topic 需要多个处理者（多播）；
- 消息速率高到不能每条深拷贝；
- handler 里要做耗时处理（必须异步）；
- handler 里需要动态增删订阅（回调内再注册）。

## 6.5 裁剪档位（如果将来要简化）

```
档位 0（当前）  零拷贝 + 允许多播 + 允许异步 + 允许回调内再注册
   │  砍掉"允许异步"
档位 1          删除 Lease / async_refs / KeepAlive.source
   │            → remove() 只等 inflight；MessageView 变为"仅同步有效"
   │  砍掉"零拷贝"
档位 2          MessageView 改为 Owned（每条消息每 handler 深拷贝）
   │            → 数据寿命问题消失，只剩目标对象寿命问题
   │  砍掉"回调内再注册"
档位 3          派发期间全程持 shared_lock，删除两个计数器与全部等待逻辑
   │  砍掉"多播"
档位 4          目录退化为 map<topic, 单个 handler>；引用计数消失
   │  再砍
档位 5          直接用 paho.mqtt.cpp（回到 mqtt_client0 形态）
```

每降一档，代码量与缺陷面显著下降，同时把对应能力交还给应用自己实现。
**选择档位的依据是需求，不是"简单"本身。**

## 6.6 演进路线（如果要继续做）

当前刻意保留的"未做"，都是可选的优化或能力扩展，按收益排序：

| 方向 | 收益 | 风险/成本 |
| --- | --- | --- |
| `dispatch` 的批次缓冲改为 `thread_local` 复用 | 去掉每条消息一次 `vector` 分配 | 依赖 I13（单派发者）；离线并发注入时需回退到局部缓冲 |
| 为"永不异步"的 filter 提供无 `Lease` 快路径 | 去掉每 handler 一次分配 | API 变复杂（需要用户在注册时声明） |
| 把生命周期协议抽成可独立测试的组件（`TopicRegistry`） | 协议与 MQTT 解耦，便于复用与形式化验证 | 抽象层增加间接 |
| 编译期开关（`MQTTX_ASYNC_SAFE=OFF`）裁剪档位 1 | 嵌入式/低功耗场景省掉一次分配 | 双份配置组合，测试矩阵翻倍 |
| 会话订阅集合持久化 | 跨进程重启也能只补差异 | 需要存储与失效策略 |
| 消息级 QoS2 状态观测 / 投递失败回调 | 更强的可观测性 | 与 paho 的 token 语义耦合更深 |

## 6.7 评审检查清单（改动本库时逐条过）

1. 新增/修改的路径是否破坏 [`02-data-structures.md`](02-data-structures.md) 的 I1–I15？
2. 有没有在持有 `mtx_` 或 `session_mtx_` 的情况下调用用户代码或可能阻塞的调用？（R1/R2）
3. 新增的等待点是否可能自等？是否需要在 `t_active_slot` 上加豁免？（R3）
4. 新的计数器是否在"`inflight > 0` 的窗口内"自增？否则会破坏两段等待的完整性证明。
5. 新引入的 `shared_ptr` / 裸指针，其生命周期是否被某个不变式覆盖？
6. 新的失败路径（异常、超时、断开）是否会把计数器留在非零状态？
7. 是否为该机制补了**能复现缺陷**的用例，并在 ASan/UBSan 与 TSan 下各跑一遍？
8. 文档（`02`/`03`/`05`）是否同步更新？

## 6.8 小结

- 保活不是炫技：它是"零拷贝的借用视图"与"任意的对象/线程所有权"并存时，
  C++ 里**没有既零开销又自动安全的第三条路**的必然结果；
- 要么每条消息强制深拷贝（简单、慢，且仍不保护目标对象），
  要么显式引用计数（零开销，但**协作式**：用户必须按值捕获视图）；
- 本库选择了后者，并把协作成本压缩到"按值捕获即可"，同时用 4 个专项用例 +
  端到端异步用例 + 两个 sanitizer 把这段协议钉死；
- **如果拿掉对应需求，应当立刻按 §6.5 降档**——复杂度只应在需求存在时被保留。
